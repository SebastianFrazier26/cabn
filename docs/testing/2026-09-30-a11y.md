## Violations found and fixed

1. **Owner's toolkit menu items had no valid ARIA parent (critical).** Axe:
   `aria-required-parent` — `role="menuitem"` buttons sat inside a plain
   `<ul><li>`, whose implicit list/listitem roles broke the
   menu→menuitem ancestor chain `role="menu"` requires. Fixed:
   `role="presentation"` on both (`OwnerToolkit.tsx`).
2. **World map minimap portals were nested-interactive inside `role="img"`
   (critical).** Axe: `nested-interactive` — the SVG's pointer-only portal
   `<rect role="button" tabIndex={-1}>` markers (a mouse convenience; the
   real keyboard/AT destination is the HTML `<button>` fieldset below, per
   the file's own existing comment) still exposed an interactive role to
   the accessibility tree despite `tabIndex={-1}`, which doesn't remove a
   node from AT browse-mode navigation, only from Tab order. Fixed: dropped
   `role="button"`/`tabIndex`/the `onKeyDown` handler entirely — a plain
   `onClick` with no role or tabindex never surfaces as an interactive AT
   node, so the mouse click still works and the duplicate is invisible to
   assistive tech, leaving the real HTML button as the only accessible path
   (`WorldMap.tsx`).
3. **Three scrollable regions with no focusable content had no keyboard
   access (serious).** Axe: `scrollable-region-focusable` — the pensieve's
   diff view, the wand's run log, and the portal preview's read-only code
   and markdown views are all `overflow: auto` with nothing inside a
   keyboard user could tab to, so they could never be scrolled without a
   mouse/trackpad. Fixed: `tabIndex={0}` + a `role`/`aria-label` on each
   (`DiffView.tsx`, `RunConsole.tsx`, `PortalPreview.tsx`).
4. **`cabn serve`'s host page had no `<html lang>` (serious).** Axe:
   `html-has-lang` — found only in the owner-mode pass, since the hosted
   demo's own `index.html` already had it; `cabn serve`'s generated page
   (`packages/cli/src/serve/hostPage.ts`) didn't. Fixed: `<html lang="en">`.
5. **No focus trap on any of these panels' Tab key.** Every modal here
   already ran its own window-capture keydown listener for Escape/Enter,
   but none intercepted Tab, so a keyboard user could Tab straight out of an
   open dialog into the hotbar or other HUD controls sitting behind it —
   confirmed for real (not by reading source) via the new
   `assertTabStaysWithin` e2e check. New shared hook,
   `packages/engine/src/react/useFocusTrap.ts`: cycles Tab/Shift+Tab among
   a container's own focusable elements, focuses the first one (or the
   container itself) on activate if nothing inside already has focus, and
   restores whatever had focus before on close. Applied to: `GuideDialog`,
   `OrbSearch`, `PensievePanel`, `UniversePickerDialog`, the sign reader
   (`SignPanels.tsx`), `SignEditor`, `PetSetupPanel` (replacing its old
   one-shot initial-focus effect), `PetChat`, and all three spellbook tool
   dialogs (`GoToLineDialog`/`SymbolPicker`/`RenameDialog` in
   `SpellbookDialogs.tsx`). `OwnerToolkit`, `EncounterBanner` and
   `WorldMap`'s own full-map dialog already had an equivalent trap (their
   own hand-rolled one, in `WorldMap`'s case) and didn't need it.
   `SpyglassPanel`/`BagTray` are deliberately left non-modal (no backdrop,
   the world keeps playing underneath, same as the existing `role="dialog"`
   set's own backdrop-having/backdrop-less split already implied) — a trap
   there would be a behavior change, not a fix, so it's not applied.
6. **Missing `aria-modal="true"`.** Present on `role="dialog"` but not
   `aria-modal` before this pass: the sign reader, `SignEditor`, `PetChat`,
   and all three spellbook tool dialogs. `OrbSearch` had neither `role`,
   `aria-label` nor `aria-modal` at all (it looked like a plain `<div>` to
   assistive tech despite behaving exactly like the other modals — full
   backdrop, focused input, blocks the world). `EncounterBanner`'s
   `role="alertdialog"` also gained `aria-modal="true"`.
7. **A real, missing focus indicator, confirmed not a headless-mode
   artifact.** The wide pass measured a computed `outline-width: 1px` on
   hotbar buttons under headless Chrome and flagged it as maybe unreliable
   there. Re-measured against a real Chrome for Testing binary (not
   Playwright's bundled headless shell): same result — Chrome's native
   `outline: auto` really does render at 1px here, on a 64×64 pixel-art
   button that already has its own 3px painted border, which makes it
   effectively invisible. Fixed: a new low-specificity baseline rule in
   `pixelTheme.tsx` — `.cabn-pixel-root :where(button, a, input, textarea,
   select, [role="button"], [role="tab"], [role="menuitem"],
   [role="checkbox"], [tabindex]):focus-visible { outline: 3px solid
   var(--cabn-accent-yellow); outline-offset: 2px; }`. `:where()` keeps its
   specificity at just `.cabn-pixel-root`, so the spellbook toolbar and its
   text inputs — which already draw their own deliberate focus treatment
   (`outline: none` + a background/color change, or a yellow `outline: 2px
   solid`) — still win the cascade unchanged. Confirmed the new ring
   actually renders: `outline-style: solid`, `outline-width: 3px`,
   `outline-color: rgb(255, 207, 77)` on the first Tab stop.
8. **The bag's closed toggle had no real accessible name.** Its only
   content was a decorative `alt=""` icon and a bare slot-count digit, so a
   screen reader announced the button as just "3" (say) rather than what it
   does. Fixed: `aria-label="Open bag (N grabbed slot(s))"`, and the digit
   badge is now `aria-hidden` (its meaning is already in the label).
9. **The victory toast had no live region.** "Victory! All bugs fixed in
   this world." appeared and auto-dismissed after 3.2s with nothing telling
   a screen reader it had happened at all. Fixed: `role="status"
   aria-live="polite"` on `VictoryToast`. (Error toasts already used
   `role="alert"`/`role="alertdialog"` — implicit assertive live regions —
   and the pet chat's log already had `aria-live="polite"`; both confirmed
   by reading source and by the axe/keyboard sweep, not just assumed.)
10. **The file view's "unsaved changes" confirm prompt had no `aria-modal`
    or Tab trap.** Same gap as item 5/6, on `FileStatusLine.tsx`'s
    `alertdialog`. Fixed the same way (added `aria-modal="true"`, wired
    `useFocusTrap`).

## Screen reader basics — confirmed clean, not just assumed

Read every panel's source and drove it through axe/keyboard rather than
sampling: dialog roles and `aria-label`s were already present on the panels
the 2026-09-29 pass spot-checked (guide, sign reader/editor, pensieve, rift,
pet setup/chat, map) — the gaps were specifically `aria-modal` and the focus
trap (items 5–6 above), not missing roles or labels. Form fields already
carry real labels: pet setup's Ollama address/region/model selects
(`aria-label`), the sign editor's file/text/offset fields (`<label>`
wrapping, or `aria-label` on the target picker), and every owner git form
field (commit message, author name/email, new branch name — all
`aria-label`). Icon-only buttons across the hotbar, spellbook toolbar and
owner toolkit already had real accessible names from visible label text or
non-empty `alt` — the bag toggle (item 8) was the one exception found.

## Reduced motion — audited, no gaps found

Read every animation source (`pixelTheme.tsx`, `portalFxStyles.ts`,
`guideDialogStyles.ts`, `ownerToolkitStyles.ts`, `WorldScene`'s monster-orbit
and layer-rise/sink call sites, `systems/sceneTransition.ts`) rather than
re-running the wide pass's single before/after screenshot diff. The
codebase already implements one consistent pattern throughout — real motion
gated behind `@media (prefers-reduced-motion: no-preference)` (opt-in,
default off under reduced motion) or an explicit reduced-motion fallback
animation, never the other way around:

- Sparkle particles, every tool's open-burst, the satchel's pop/flap, the
  spellbook's book-open and its border motes, the wand-cast icon, the
  rune-ring spin, the crystal ball's rise, the spyglass's sheen and
  iris-open, the orb/crystal-ball mist swirl, the hotbar's hover sheen, and
  the victory confetti: all `no-preference`-gated, each with a plain-fade or
  static fallback under reduced motion.
- The encounter popup's shake is gated the same way; its brief opacity
  flash is *not* gated, per its own comment — an opacity pulse isn't the
  vestibular-motion category the setting targets, only the positional shake
  is.
- Monster orbits (`render/monsterOrbit.ts`'s `MonsterOrbits`), the world
  layer's rise/sink (`layerRiseMs`), and the scene-transition's cabin delay
  are all constructed with `prefersReducedMotion()` read live at call time
  in `WorldScene.ts`, not hardcoded.
- The scene-transition bars/wipe already had their own
  `@media (prefers-reduced-motion: reduce) { animation: none !important;
  display: none; }` override.

Nothing here needed a fix. Documenting "checked, found clean" rather than
manufacturing a change.

## Contrast

`packages/engine/tests/editorThemeContrast.test.ts` already covered every
quill/pensieve syntax and diff color pair. New sibling,
`packages/engine/tests/uiContrast.test.ts`, covers the plain UI chrome that
one doesn't: the fixed dark button/badge ink (`#201a3d`, used on every
`.cabn-btn` variant, the rename preview's ins/mark, the owner toolkit's "on"
badge, the guide's confirm pill, the speed toggle's active state) against
each bright accent fill, the `.cabn-segmented`/owner-toolkit `kbd` chip
(panel-body-on-border-outer and white-on-border-outer), the pet chat's error
text, the file view's "unsaved" marker, and the guide's "▼ more" cue — 9
pairs × day/night/crimson.

**10 of the 27 checks came back below WCAG AA (4.5:1) for text** — all
pre-existing (nothing this pass touched), on colors the design brief fixes
(Meadow/Berry/crimson tokens, DotGothic16) — so per this task's instruction,
**reported here, not recolored**:

| Theme | Pair | Ratio | Needs |
|---|---|---|---|
| Day | button/badge ink on violet (rename mark) | 4.17:1 | 4.5:1 |
| Day | pet error text on panel body | 2.88:1 | 4.5:1 |
| Day | unsaved marker (●) on panel body | **1.35:1** | 4.5:1 |
| Day | guide "▼ more" cue on panel body | 2.09:1 | 4.5:1 |
| Night | button/badge ink on violet (rename mark) | 3.56:1 | 4.5:1 |
| Night | panel-body text on border-outer chip | 2.33:1 | 4.5:1 |
| Crimson | button/badge ink on pink (cancel) | 3.50:1 | 4.5:1 |
| Crimson | button/badge ink on violet (rename mark) | 3.16:1 | 4.5:1 |
| Crimson | panel-body text on border-outer chip | 2.10:1 | 4.5:1 |
| Crimson | pet error text on panel body | 3.86:1 | 4.5:1 |

The day theme's yellow "unsaved" dot (`--cabn-accent-yellow` on
`--cabn-panel-body`, 1.35:1) is the worst of these by far — barely visible
text-on-near-white, not just short of AA.

Each pin is a `test.fails` in `uiContrast.test.ts` (same convention the
2026-09-29 pass used for the Python self-import false positive: a test that
documents the *current* broken state on purpose, so a future fix has to
touch this file deliberately rather than silently start passing or
silently stay broken). **This needs a design decision, not a one-line
fix** — options:

1. **Darken the accent used as text/ink in each failing pairing** (the
   violet accent for the button ink case, the pink/violet accents
   elsewhere) the same way `editorTheme.ts`'s syntax colors were
   hand-darkened from their accent-* base — keeps the same hue family, only
   changes lightness.
2. **Stop reusing raw `accent-*` tokens as text color** in these four spots
   (pet error, unsaved marker, guide more-cue) and give them their own
   AA-safe variants, the same way the editor's `syntax*`/`diff*` tokens
   already exist alongside the accents they're derived from.
3. **For the border-outer chip pairs** (segmented-selected, the owner
   toolkit's kbd): either swap which token is foreground vs background
   (text in `--cabn-text`, background in `--cabn-border-outer` tinted
   differently) or add a border-outer-safe text token.
4. Leave the fixed `#201a3d` button ink as-is for green/yellow/cyan (all
   already comfortably clear AA) and pick a *second* fixed ink for
   violet/pink fills specifically, mirroring how `.cabn-pet-chat` bubbles
   already switch ink via `inkFor()` based on the fill's own luminance —
   that function could plausibly generalize to the button/badge case too.

No opinion recorded here on which — that's the user's call per this
project's own design-decision rule, not something to pick silently.
