## Bugs, ranked by severity

### 1. (High) World-bake time scales far worse than linearly with cluster count — a ~2000-portal world may never finish entering

**Repro:** `cabn serve <dir> --offline`, open `?e2e=1&perf=1`, wait for the
`cabn:world:bake-end` performance mark.

- `flask` world (42 clusters, 217 portals): `cabn:world:bake-start` → `cabn:world:bake-end` = **14.2s**, of which `ground-field-baked` alone took **9.3s** (575ms → 9880ms).
- This repo's own world (145 clusters, 1997 portals, 3.5x the clusters): the same mark sequence **did not complete within 120s** on two separate runs (one bare 120s timeout, one with an extra 120s grace period after — killed at ~240s+ with `bake-end` still not observed). The page also stopped responding to further Playwright `evaluate()` calls once stuck, consistent with the bake running synchronously on the main thread with no yield points.

3.5x more clusters produced at least 17x worse (and possibly unbounded) bake
time, not ~3.5x — this is disproportionate, not just "big worlds take
longer." `cabn:world:ground-field-baked` is the dominant single phase in the
`flask` breakdown (9.3s of 14.2s), so it's the prime suspect.

**Where:** `packages/engine/src/scenes/WorldScene.ts:1148` calls
`bakeGroundField()` (`packages/engine/src/render/groundField.ts`), which
tiles the world's full bounding box into 512px chunks (`FIELD_CHUNK_TILES`,
`groundField.ts:14-34`) and bakes each with a per-tile Phaser draw. This is
already a known, partially-mitigated issue on this branch — commit
`eacb1f5` ("Shrink ground-field bake bounds; cap e2e worker concurrency")
already diagnosed "9-47s world-load times" and cut the *margin* term in
`computeWorldBounds` (`packages/engine/src/render/worldBounds.ts:50-66`).
But that margin (`MIN_BOUNDS_MARGIN_PX`/`MIN_FOLLOW_ROOM_PX`, lines 12-27) is
a small constant, and the bounds themselves are `min(0, ...clusterXs) -
margin` to `max(0, ...clusterXs) + margin` (lines 61-64) — for a world with
many spread-out clusters, the *cluster position spread itself* (i.e.
whatever `packages/converter/src/layout.ts` does to place 145 real clusters
vs. the demo's own small handful) dominates, not the margin the prior fix
addressed. That prior fix targeted the demo's own sample worlds
(72/56 and 36/30 chunks); it doesn't obviously help a real repo conversion
at this scale, and the data above suggests it doesn't. I didn't get far
enough to confirm layout.ts's placement is the actual quadratic-or-worse
term, only to confirm the bake-time effect and localize the mechanism.

**This needs a design call, not a one-line fix** — options include capping
bake area, chunking the bake across frames (yielding), or deferring
far-from-spawn chunks. Reporting, not fixing.

### 2. (High) `from . import <submodule>` inside `__init__.py` is misread as a self-import cycle (false positive, common Python idiom)

**Repro (added as a pinned regression test):**
`packages/converter/test/annotate/circularImport.test.ts` — new test "from .
import <submodule> in __init__.py is mis-flagged as a self-cycle".

Real-world hit: `pallets/flask`'s own bundled example apps —
`examples/celery/src/task_app/__init__.py:22` (`from . import views`) and
`examples/tutorial/flaskr/__init__.py:30` (`from . import db`) — both flagged
as `OuroborosError` ("Circular import between 1 file: `__init__.py` ->
`__init__.py`"), even though neither file imports itself; each imports an
ordinary sibling module. `from . import x` is one of the most common Python
package idioms there is (deferred blueprint/view registration inside a
factory function), so this false positive will fire on a large fraction of
real Flask/Django-style codebases.

**Root cause:** `resolvePyTarget` in
`packages/converter/src/annotate/importGraph.ts:209-222` already documents
(in its own doc comment) that a bare `from . import x` is ambiguous between
"import submodule x" and "import name x from `__init__.py`", and picks the
second reading unconditionally, resolving to the current file's own
`__init__.py`. `circularImport.ts:59-61`'s `isSelfLoop` check then reports
that resolved self-edge as a genuine one-file cycle. The ambiguity itself is
a documented, accepted simplification; the consequence — a same-file
self-edge from that simplification tripping the *self-import* detector,
specifically for the single most common way to write `from . import x` —
wasn't called out. Fixing well means resolving `x` against the package's
real file listing (is there a sibling `x.py`/`x/`? if so it's a submodule
import, not a self-reference) — a design change, not a typo fix. Reporting,
not fixing.

### 3. (High) A single file's scanner cascade can generate ~1000 duplicate monsters, drowning out everything else in a world

**Repro:** `cabn build changesets/changesets --offline` → 1114 total
monsters, of which **998 (90%)** are `IoError`/`bracket:unterminated-string`
findings from one file:
`packages/apply-release-plan/src/get-changelog-entry.test.ts`. That file is
74 lines of ordinary Vitest `toMatchInlineSnapshot` calls with multi-line
backtick template literals containing markdown text (nested `"`/`'`
characters inside the backtick string) — real code, not malformed.

**Where:** `packages/converter/src/annotate/bracketBalance.ts` — its own doc
comment (lines 24-28) already documents the exact failure mode: "no re-sync
after the first mismatch... which can cascade into a second reported issue
that's really the same root cause." What that comment doesn't anticipate is
the cascade's real-world scale: not "a second issue" but 998 issues from one
74-line file, which then dominates the entire world's monster population
(998 of 1114) for a 316-portal repo. Contrast with
`packages/converter/src/annotate/run.ts:23-24,277,282`, where
externally-injected findings (SARIF/ESLint) already have exactly this kind
of cap (`MAX_EXTERNAL_PER_FILE`, `MAX_EXTERNAL_TOTAL`) — built-in annotators
like `bracketBalance` have no equivalent. Recommend applying a similar
per-file (and maybe per-rule) cap to built-in annotators, or having
`scanCode` bail out after the first unresolved mismatch on a given
line/string-run instead of continuing to misparse the rest of the file. Both
are behavior changes with tradeoffs (a cap silently hides real issues past
the Nth; bailing early could miss real issues later in the same file) —
reporting, not fixing.

## Robustness fuzzing

All of the following pass; see "Tests added" below for exact assertions.

| Case | Result |
|---|---|
| Empty directory | `DirSource` yields zero entries, no crash |
| 50 levels of nesting | Walked correctly, posix-separated path, content intact |
| Unicode/emoji filenames (café, 文件, 😀, naïve) | Round-trip correctly through path and content |
| Symlink loop (dir symlink pointing at its own parent) | Skipped, not followed — confirmed terminates, doesn't hang |
| File symlink | Skipped, not read through |
| Binary-only directory | Walked without decode errors, bytes preserved |
| Single file far over `maxFileBytes` (real fs, not fake source) | Capped to metadata-only by `walk()`, as designed |
| 5,000 tiny files (real fs) | `DirSource` itself yields all 5,000; `walk()` correctly truncates to `DEFAULT_MAX_FILES` (2000) and reports `truncated`/`skippedFiles` |
| Zip path traversal (`../`, absolute, backslash, double-slash, dot-segment) | Already covered by pre-existing `test/zip-security.test.ts` — reran, still passes |
| Zip bomb (high-ratio single entry, entry-count cap, archive-wide byte cap) | Already covered by pre-existing `test/zip-security.test.ts` — reran, still passes |

**Gap found and filled:** `DirSource` (the real-filesystem walker used by
every `cabn build <dir>`/`cabn serve <dir>` invocation) had **zero** direct
test coverage before this pass — `walk.test.ts` only ever drove `walk()`
against an in-memory fake `FileSource`, never the real `node:fs`-backed
`DirSource`. All of the real-fs cases above are new coverage for a
previously-untested code path, not just fuzz inputs.

## Recommended fixes, ranked

1. **Bug 1 (world-bake scaling)** — the margin-only fix in `eacb1f5` doesn't
   cover this; profile `bakeGroundField`/`computeWorldBounds` against
   `packages/converter/src/layout.ts`'s cluster placement at real
   repo-conversion scale (dozens to low hundreds of clusters), not just the
   demo's own small sample worlds. This blocks entering any world near the
   current file/portal caps and should be the top priority before those caps
   are ever raised.
2. **Bug 3 (bracket-scanner cascade)** — add a per-file (and/or per-rule)
   cap to built-in annotators mirroring `MAX_EXTERNAL_PER_FILE`/
   `MAX_EXTERNAL_TOTAL` in `run.ts`, or have `scanCode` stop after the first
   unresolved mismatch per scan region. Directly affects world playability
   (990+ duplicate monsters from one file is a bad experience regardless of
   correctness).
3. **Bug 2 (Python self-import false positive)** — resolve bare
   `from . import x` against the package's actual file listing before
   deciding it's a self-reference; affects a large fraction of real-world
   Python packages.
4. **NullTypeError markdown multi-target links** (false-positive sampling,
   unconfirmed root cause) — worth a follow-up look at comma-separated
   markdown link targets.
5. Fill the descoped items: full viewport matrix, in-browser walks for
   `changesets`/`tldr`, a real screen-reader/axe pass, and dialog-level
   keyboard focus-trap checks for spellbook/map/pet panels.
