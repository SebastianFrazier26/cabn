# Changelog

## 2026-09-29 — Demo worlds rebuild when stale; monsters keep their lines when you re-enter an edited file

- **Fix: the demo stops serving a stale world.** `apps/demo/scripts/build-world.mjs` (predev, prebuild, `build:world`) used to convert a world only if its `world.json` was missing, so after converter or fixture changes the old world stayed, and e2e runs and postbuild checks failed until someone ran `build:world -- --force`. Each world (`sample` and `notes`) now gets a fingerprint: a sha256 over its source tree (paths and bytes, `cabn.json` included), its findings file and build options, the version and built `dist/` contents of `@cabn/world-schema`, `@cabn/converter` and `@cabn/cli` (without the cli's bundled sprites), the world-schema `CABN_VERSION`, and `gen-git-fixture.mjs`. The fingerprint is stored in `apps/demo/node_modules/.cache/cabn-worlds/<name>.txt`, outside `public/`, so it never ships. A world whose fingerprint is missing or different is cleared and rebuilt. An up-to-date check takes about 0.3s for the whole script. `--force` still rebuilds everything. The first run after this change rebuilds both worlds once. Details are in the README's "Run the demo" section.
- **Fix: monsters start on the right line when you re-enter a file with saved edits.** `WorldScene` used to hand `FileScene` each monster's build-time line, so after a save that moved code (lines inserted above a monster), the next visit and every visit after a reload showed the monster on its old line until the next save. Now, when you enter a file that has a saved edit (`save.fileOverrides`), its monsters are re-checked against the saved text with the same annotator re-run a save uses. `recheckMonster` in `systems/battle.ts` gives the save's fixed/not-fixed verdict (`checkMonsterFixed` now calls it) plus the bug's current location. `relocateMonsters` applies that to a file's monsters. The result is cached per portal and saved text, so an unchanged file isn't re-checked on the next entry, and nothing runs per frame. The same pass runs once at world load for every edited file, before the orbits are drawn. That way a saved edit that never went through a save's re-check (a stash restored from the rift) can't leave monsters it fixed orbiting the arch or counted in the HUD.
- **Same rules as a save.** A monster the saved text fixed is defeated the way a save defeats it: recorded in `defeatedMonsterIds`, removed from its orbit and the counter. Surviving monsters move to the line where the re-run annotator (or the ouroboros' import, or an external finding's flagged line) finds them now. A save never spawns new monsters (new problems appear only in the spellbook's live list), so re-entry doesn't either.
- **Fix: five monster kinds no longer die when code above them moves.** The todo, bracket, broken-import, encoding and json-parse annotators used to put the finding's line and column in its rule. So inserting a line above a TODO wisp, gremlin, ghost, warded mimic or rot-sprite and saving counted it as fixed. Their rules are now keyed on content:
  - todo: `todo:<marker>:<hash of the normalized note text>`
  - bracket: `bracket:<kind>:<char>:<hash of the normalized line>`
  - broken-import: `broken-import:<specifier>`
  - encoding: `encoding:replacement-char`
  - json-parse: `json-parse:<hash of JSON.parse's message with V8's "at position N" and "(line L column C)" removed>`

  Identical findings in one file get the usual `#2`, `#3` occurrence suffix (`uniquifyRules`). `error.loc` still holds the line, for display and positioning only. So blank lines above one of these monsters leave it alive on its new line, and fixing the problem still defeats it. The encoding mimic now stays until every U+FFFD is gone, not just the first one. The json-parse key relies on V8's wording, which the Node build and the Chrome re-check share. Another engine (Safari/Firefox) words it differently and would count the rot-sprite fixed on its first save, as the old key already did there.
- **One-time reset of defeated progress for these five kinds.** Monster ids hash the rule, so every wisp, gremlin, ghost, warded mimic and rot-sprite gets a new id. Existing saves' `defeatedMonsterIds` for them no longer match, and those monsters come back once. There is no migration, by decision. Other species keep their ids and progress. Rebuilt worlds pick up the new ids; the demo's world fingerprint rebuilds its worlds automatically after the converter changes. `apps/demo/e2e/embed-monsters.spec.ts` now picks the monsters it moves by their home portal instead of hard-coded ids.
- **`@cabn/converter`:** new `externalFindingLine(rule, content)` (exported from `./core`), the line an external finding's flagged text is on now. `checkExternalFindingFixed` is defined in terms of it and behaves as before.
- **Tests:** `apps/demo/tests/build-world.test.mjs` (stale/forced/up-to-date decisions; fingerprint stable under touch-only changes; changes with source, `cabn.json`, a new file, findings, converter version or dist, schema version and fixture generator; the cli's sprites ignored). `packages/engine/tests/battle.test.ts` (relocation for dead code, ouroboros and external findings, fixed monsters reported; for each of the five re-keyed kinds, lines inserted above don't fix it and fixing the problem does). `packages/converter/test/annotate/externalFindings.test.ts`, new `packages/converter/test/annotate/positionFreeRules.test.ts` (same rule after lines are inserted above while loc moves, occurrence indexes, note-text keying, `jsonErrorKey`). New `apps/demo/e2e/monster-reentry.spec.ts`: insert three lines above `lib/models.py`'s skeleton, save, leave, re-enter, reload, and check both its tracked line and its sprite row each time (fails without the fix). A second test saves a blank line above `gardeners.ts`'s TODO wisp and checks that it survives on the moved line, with no defeat recorded, and again after re-entry.

## 2026-09-29 — Clearings grow tall enough to hold their arches

- **Fix: top and bottom portal arches no longer stick out of their clearing.** A clearing's ground was an ellipse 0.65 as tall as it is wide, while its arches sit on a circle, so the roof of a top arch and the base of a bottom arch hung past the grass (for the smallest ring, radius 180, the ground's half-height was ~175px against arches reaching 276px). The half-width and every cluster position are unchanged; only the half-height grows, and only as far as the cluster's actual ring needs: `ry = max(0.65 · rx, max over arches of (|y ± 96| + 12) / √(1 − (x / rx)²))`, where (x, y) is each arch's centre relative to the clearing, ±96px is the 2x arch's roof and base (measured from the sprite alpha) and 12px is the grass margin. A ring whose arches all sit near the horizontal keeps today's height exactly. In the sample world clearing half-heights go from ~176px to 218–306px (the root from 327 to 512), so most clearings are now about round.
- **One formula for engine and converter:** the math lives in `@cabn/converter`'s new `clearingFit.ts` (exported from `./core`), used by `WorldScene`. The ground bake, tint, flower ring, prop and decal scatter use the new half-height; path-corridor exclusions, the spawn keepout and the edge-scenery keepout use the larger of the two radii. Signs keep using the half-width (the clearing only grew, so nothing they could reach moved off the grass); the world map draws fixed-size dots and is unaffected.
- **Layout is unchanged.** `layout.ts` and `shadowLayout.ts` still space clearings by the half-width, so no normal or shadow cluster moves. The new `CLEARING_HEIGHT_OVERSHOOT_PX` (18) bounds how far past the half-width any ring can push the height; two of them fit inside `CLEARING_GAP_PX` (60), and a converter test checks that for every portal/path count.
- **Only the arch's height is fitted, not the pillars' full width.** With the width fixed, containing the outer pillar of an arch near the side of the ring would take a half-height of ring + ~190px, turning clearings into tall ovals that overlap their neighbours by up to 110px in the sample world. The top and bottom arches still fit whole, pillars included.
- **Tests:** unit tests in `packages/converter/test/clearingFit.test.ts` and `packages/engine/tests/clearingFit.test.ts` (every ring slot's arch inside the ellipse for rings of 1–40 with several path layouts; top/bottom arches' full silhouette inside; rings that already fit unchanged). New `apps/demo/e2e/clearing-fit.spec.ts` checks every arch sprite's roof and base against its clearing in the running sample world at 1280×720; `CABN_REVIEW_SHOTS=1` writes before/after day/night shots to `assets/generated/review/clearing-fit/`.

## 2026-09-29 — Monsters stay visible on web arches; the dock clears the arch at narrow widths

- **Web-arch orbit.** A url-preview arch's live mini-page is a DOM layer over the canvas, so monsters orbiting that arch used to vanish under it. Their orbit is now a function of portal kind (`portalOrbitEllipseFor` in `systems/monsterOrbit.ts`): other arches keep today's ellipse, and a web arch gets `webPortalOrbitEllipse`. That loop is centred on the opening and sized so its smallest wobbled ellipse still encloses the opening, grown on every side by the largest sibling's sprite reach (`monsterClearancePx`: half size at the near-point perspective scale, widened for sway and spin, plus the bob). Any loop around the arch has to cross above and below the ~125px-tall opening, so this orbit is wider and taller than the arch orbit (about 330x250 px for the demo's species), not flatter. Its far pass sits behind the capstone. Unit tests check that every path point, and every species' drawn bounds over many laps, stay outside the opening and its projected on-screen iframe rect.
- **Dock placement at narrow widths.** `portal:web-rect` now carries a `keepout` rect: the arch sprite plus the reach of any live monsters orbiting it (`MonsterOrbits.portalReach`). `placeDock` (new `systems/dockPlacement.ts`) keeps the dock's usual right-hand spot and width when that clears the keepout. Otherwise it narrows the dock down to 320px. If that still overlaps, it moves the dock to the left edge, away from the arch, between the settings corner and the monster counter. If nothing fits, it uses 320px on the side that overlaps less. A narrowed dock lays its page out narrower (`dockLayoutWidth`, page scale kept at 0.65 or above, 360-640px) so text stays readable. At 1280px with no monsters on the arch, nothing changes. `PortalPreviewDock` takes an optional `bus` prop; without it the dock never moves.
- **Minimap yields to the dock.** While the preview dock is open (`previewDockOpen`, the same rule the dock renders by), the minimap is hidden so it no longer draws over the dock's header. M still opens the full map.
- **e2e:** `apps/demo/e2e/embed-monsters.spec.ts` moves three monsters onto `docs/threejs.md` by rewriting `world.json` in the browser. At 1024x768 and 1280x800 it samples 16 frames to check that no monster sprite's bounds meet the mini-page. It also checks that neither the dock nor the docked page covers the arch, that the minimap is hidden and the dock header is on top, and that the minimap comes back on leaving. A third test checks that at 1280 without monsters the dock keeps its 480px right-hand spot. Review shots are in `assets/generated/review/embed-monsters/`.

Signs in hidden folders can be written (with `realm: "shadow"`) only while the realm shows.

## 2026-09-28 — Hidden files leave normal worlds; shadow realm data and security (M1)

- **Behaviour change: normal worlds no longer show hidden files.** Any path with a segment starting with `.` (`.env`, `.gitignore`, `src/.eslintrc.json`, everything under `.github/`, `.vscode/`, `.husky/`, ...) is left out of every normal world: `cabn build`, `cabn serve`, the backend's `POST /v1/worlds`, hosted bundles, and universes converted in the browser. This works like `ls` without `-a`. Rebuilt worlds have fewer portals (the demo's `sample-project/.gitignore` is gone from it). `walk()` gains `hidden: "exclude" | "only"` (default `"exclude"`) and `isHiddenPath()`. Ignored folders (`.git`, `.venv`, `.next`, ...) stay out of both. A `cabn.json` override naming a hidden file is now skipped instead of failing as a typo, and one whose `src` is a hidden file is refused. Git history is unchanged: it keeps hidden files as they are in git, and secret-pattern files are still never shipped from any commit. Existing demo worlds need `pnpm -F @cabn/demo build:world -- --force`.
- **Shadow realm data (owner only).** `convertShadow(source, baseManifest, opts)` (`@cabn/converter` Node entry only, never `./browser`) turns the hidden files into a `WorldLayerDelta` over the base world. The delta holds extra clusters (a per-folder annex `<clusterId>#shadow` for dotfiles, own clusters for dot-folders), paths, portals, monsters, signs, per-cluster chunks, a minisearch index and each text file's SHA-256. Annotators run over visible and hidden files together, keeping only monsters on hidden portals or shadow paths. Secret-named hidden files are readable here (a visible secret file stays sealed and out). A magpie on one appears only when git tracks the file. Hidden media is a sealed chest. `shadowLayout.ts` places the new clusters in a second pass that never moves a base position (outward in 60px steps, 72 angles ordered by the widest free gap around the parent and away from the root). `layout.ts` now exports `estimatedClearingRadius` and `CLEARING_GAP_PX`.
- **`@cabn/world-schema` `layer.ts`:** `WorldLayerDeltaSchema` and `WorldLayerManifestSchema` (the delta minus chunks and search index) reuse the existing cluster, path, portal, monster, sign, chunk and search-index schemas. `baseGeneratedAt` lets a stale delta be refused (`worldLayerIssues` / `assertWorldLayerFits` also check id collisions and dangling references). JSON Schemas: `world-layer-delta.schema.json`, `world-layer-manifest.schema.json`.
- **`cabn serve --owner` shadow routes** (`serve/ownerShadow.ts`): `GET /owner/shadow/manifest`, `GET /owner/shadow/chunk/<clusterId>`, `GET /owner/shadow/search-index`, `POST /owner/shadow/save`. All go through `checkOwnerRequest` and answer `Cache-Control: no-store`. Without `--owner` they answer 404. The layer is computed on the first request and cached in the serve process. The cache is cleared on reconvert and whenever the base `generatedAt` changes. It is never written into the bundle, so nothing hidden is reachable under `/world/*`. A save needs `{ path, content, baseSha256 }` and answers 409 on a hash mismatch. It edits only an existing hidden text file from the layer: no symlink hop, not in the git directory, a regular file. It is written to disk only and never committed. The body is capped at 2 MB and the content at 512 KB, and contents are never logged.
- **Shadow signs:** `/owner/signs/save|delete` accept `realm: "shadow"` for signs in hidden folders (never `.git` or an ignored folder, case-insensitively; the name starts with a letter or digit). They update only the cached layer, never `signs.json`. The normal realm still refuses hidden folders.
- **Atomic writes keep file modes.** The temp-file-and-rename write moved into `ownerAuth.ts` (`overwriteFileAtomic`) and now preserves the original permission bits: shadow saves and sign overwrites no longer reset a file to 0644. The no-symlink-hop, not-in-gitdir and regular-file checks are shared as `resolveExistingOwnerFile` (owner git commits use it too).
- **Leak tests:** a converter canary fixture (`.github/ci.yml`, `.vscode/settings.json`, `src/.eslintrc.json`, `.env`, each with a unique `SHADOW_CANARY_*`) checked across every bundle key and value. Also a `cabn build` output canary, a check that `build.ts` never imports the shadow realm, an import-graph test proving `browser.ts` can't reach `shadow.ts`/`shadowLayout.ts`, and a backend zip-upload canary. Serve tests cover the 404s without `--owner`, the 403s (no token, cross-site, bad Host, foreign Origin), `/world/*` staying clean before and after the layer is computed, save conflicts, symlinks, `.git`, new files, mode preservation, sign realms, cache clearing and magpie-only-if-tracked. A layout invariant checks that the base `world.json` and its portal-ring data are byte-identical with and without hidden files; other layout tests cover non-overlap, a deterministic snapshot and 30 hidden folders at the root.
- **Demo:** the postbuild step gains `check-no-shadow-in-bundle.mjs`. It fails the build on shadow wire strings or client names in `dist/**/*.js`, on a `shadow/` asset folder, or on any hidden path in a world manifest, chunk, search index or signs file under `dist/worlds` and `public/worlds` (the `git/` pack directory and `releases.json` exempt: the git pack keeps hidden blobs, by design).

## 2026-09-28 — Shrink the ground-field bake area; cap e2e worker concurrency

- **Smaller, camera-derived world bounds.** `render/worldBounds.ts` (new, pure, unit-tested) replaces WorldScene's and ShelfScene's identical flat-margin `computeWorldBounds` (one combined `max(500/400px, viewport/2 + 150px)` margin applied to all four sides, regardless of axis) with a per-axis margin — half that axis's own viewport dimension, plus a small fixed `MIN_FOLLOW_ROOM_PX` (150px) the camera needs to actually pan rather than sit dead-centre — padded around cluster/cabin extents. Shrinks the sample-project world's baked ground-field chunk count from 72 to 56 (18,432 → 14,336 tile draws) and notes-vault's from 36 to 30 chunks (9,216 → 7,680 draws) at a 1280×720 viewport; a same-machine, back-to-back `perf-measure.mjs --reps=6` run measured shelf→world median time dropping from 1527ms to 1263ms (17%) under identical conditions. New `apps/demo/e2e/world-bounds.spec.ts` scrolls the camera to all four bounds corners (read back live via `camera.getBounds()`, not recomputed independently) at 1280×720 and 1920×1200 and asserts none show the raw scene background colour; verified it fails against a deliberately-too-small margin before confirming it passes against the real one. **Found via that same e2e work:** an initial version of this fix used exactly half the viewport with no follow-room term, which made bounds width/height exactly equal the viewport whenever every cluster/cabin shares an axis coordinate (this demo shelf's two cabins are both at x=0) — zero camera scroll room, so `startFollow()` could never pan and the camera stayed dead-centre on the origin regardless of player position. Caught by `e2e/smoke.spec.ts`'s click-to-move assertion failing deterministically (confirmed via `git stash` bisection, not a flake); `MIN_FOLLOW_ROOM_PX` fixes it.
- **e2e workers capped relative to CPU cores.** `apps/demo/playwright.config.ts` now sets `workers` to a quarter of `os.cpus().length` (floor, minimum 1) instead of Playwright's own default of half the cores — each worker launches a full Chrome process that spends real wall-clock time in the (still real, ~1.3-3.8s per world entry per the perf-measure numbers above) synchronous ground-field bake, and several of those competing for the same cores at once is what reproduced this milestone's reported 9-47s world-load times in measurement, not server or network contention. An explicit `--workers=N` on the CLI still overrides this, per Playwright's own precedence.

## 2026-09-28 — AI pet: redact, don't withhold, a magpie-guarded file

- An undefeated magpie (leaked-secret monster) used to make `read_file` and `propose_edit` refuse a file outright. It now sends the file with only the secret values swapped for a fixed `«redacted secret»` marker, so the pet can still help with the rest of it; the tool result also tells the model how many secrets it redacted. Once the secret is actually removed (the magpie defeated), the file goes through untouched, as before.
- Redaction reuses the exact spans the `leakedSecret` annotator (`packages/converter/src/annotate/leakedSecret.ts`) flags — a new `findLeakedSecretSpans` export there, uncapped (unlike the annotator's 5-monster cap, since a 6th secret still has to be redacted) but otherwise identical detection. A private-key span (the annotator only anchors on the PEM header line) is extended through its matching `-----END ... KEY-----` line so the key body itself doesn't ship; a multi-line span redacts to one marker per line so line numbers stay valid for `propose_edit`.

  - **Richer default previews, additive (no `cabnVersion` bump)**: `Portal` gained an *optional* `richPreview` field (`@cabn/world-schema`'s `preview.ts`) — a discriminated union (`code` with a language id and bumped caps [40 lines/200 chars/4KB, up from the compact panel's 12/120/512], structured `markdown` [headings/paragraphs/lists/fenced code as data, not HTML — a preview renderer never needs `dangerouslySetInnerHTML`], a copied-in `image` [bundle asset path + byte-header-sniffed dimensions], a `text` blurb, a live `url`, or `sealed` for binaries) built by `@cabn/converter` for every portal (`richPreview.ts`, `markdownPreview.ts`, `imageDimensions.ts`) and resolved from a `cabn.json` override when one applies (`cabnConfig.ts`).   - **`@cabn/engine`'s `PortalEmbed`** (`react/PortalEmbed.tsx`): the live sandboxed iframe for a `url` override. `sandbox="allow-scripts allow-same-origin allow-forms allow-popups allow-popups-to-escape-sandbox"` (each flag reasoned about in the component's own doc comment — allow-same-origin/allow-forms are kept because the framed origin is always third-party and dropping them breaks most real sites' own sessions/forms, not because they're free of risk), `referrerPolicy="no-referrer"`, `loading="lazy"`, `allow=""`, never `allow-top-navigation`. A per-process `crypto.randomBytes(32)` session token, printed in the URL and required on every exec request via `x-cabn-token`, compared with `crypto.timingSafeEqual` (`security.ts#constantTimeEqual`, length-checked first so mismatched-length buffers never reach it) — missing or wrong token is a 403 (`security.test.ts`, `server.test.ts`). `Host` must be exactly `127.0.0.1:<port>` or `localhost:<port>` (`isLoopbackHost`, defeats DNS rebinding — an attacker's domain still sends its own name as `Host`, not `localhost`); `Origin`, if present, must match the same way (`isAllowedOrigin`) — both tested directly and via a raw `node:http` request against the running server (`fetch()` forbids overriding its own `Host` header, so that one test bypasses `fetch` entirely). - Asset pipeline art-direction pivot (M2 follow-up): the soft-rendered 1024² originals, not the crisp recovered sprites, are now the in-game art. `matte-originals.ts` reuses the same background-classification grid to cut a feathered alpha matte over the untouched original pixels (`assets/generated/originals/<name>.png` at 1024/512/256, plus 512/256 WebP). `soften.ts` is a new hand-rolled style pass (per-cell neighbor-luminance gradient shading, deterministic per-cell jitter and per-pixel grain, bloom bleed around bright cells, feathered silhouette edges) that turns a crisp pixel-map render back into the source art's soft-chunky look; calibrated by placing `soften(cabin_64)` next to the original `cabin.png` in the preview page. Palette gained 4 curated cool colors (steel gray, bone/moonlight white, pale ghost blue, cool shadow blue-gray) appended after the extracted 28, since the source icons have no cool neutrals. Ghost and character_idle placeholders redrawn (curvier wavy-tailed ghost in the new cool tones; Pokémon-BW-style big-head/short-body character); portal_arch kept as-is. `recover-sprites.ts` refactored to share `computeBackgroundGrid` with the new matte script instead of duplicating it.
